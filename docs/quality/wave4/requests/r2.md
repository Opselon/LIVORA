- **R-r2-1 | server/tests/Livora.Server.Tests/Fixtures/LivoraWebFixture.cs + server/src/Livora.Server/Program.cs | make the fixture's `ConnectionStrings:Livora` override actually reach the host** |
  Executed fact at 1c7bd50+ (this branch): `Program.cs:29-31` reads `Database:Provider` and
  `GetConnectionString("Livora")` and passes the *values* into `AddLivoraDbContext` — before
  WebApplicationFactory's deferred `ConfigureAppConfiguration` takes effect for those reads. Result:
  every fixture in the test process shares `<test bin>/livora.db` (the appsettings default), NOT the
  intended per-fixture `DbDir/fixture.db` the class-doc advertises ("Database:Provider=inmemory… a
  test never touches a file DB, so parallel runs cannot collide" → the newer per-file docstring says
  "isolated temp SQLite"). Two hosts writing one SQLite file concurrently is a real collision risk
  (busy-timeout + WAL make it *survive*, not *isolated*), and `DisposeAsync` deletes a dir that was
  never written. Fix shape is the lead's call: either resolve the connection string lazily inside
  the `AddDbContext` options lambda (so the final, post-configuration value wins), or let the
  fixture pass its string via an `Action<DbContextOptionsBuilder>` override.
  **Blocking? no** — the identity test harness works around it by resolving the file that actually
  holds the live schema (`IdentityApiHarness.ResolveLiveDatabase`) and by keeping every test's
  emails/ids unique, but the platform fact is wrong and every future lane inherits it.

- **R-r2-2 | docs (frozen §5/§5c reconciliation) | record the `GET /auth/sessions` shape ruling** |
  §5 says every list endpoint returns `PagedResult<T>`; §5c freezes this endpoint's response as the
  bare array `[{sessionId, deviceLabel, …}]`, and the frozen P1-D client
  (`Infrastructure/Cloud/LivoraApiPort.GetSessionsAsync` → `IReadOnlyList<SessionInfoDto>`)
  deserializes exactly that. More-specific frozen contract wins: the handler now answers the array
  (optional `offset`/`limit` still bound the page). `Sync/operations` keeps `PagedResult` (it is
  additive to §5c, so §5 governs). Needs a line in the contract ledger so Phase-2 lanes don't
  "fix" it back. **Blocking? no.**

- **R-r2-3 | server/src/Livora.Server.Infrastructure/Identity/IdentityEntities.cs (DONE in-lane, noted for the merge) | IdentitySideDbContext deleted** |
  The R-p1c-1 precondition (contributions breaking the frozen pre-Wave4P1Schema migration test) is
  gone: runtime registration (IdentityModule.ConfigureServices) and design-time registration
  (HostDesignTimeFactory) both feed the single shared model the Wave4P1Schema migration was
  generated from; the side context was dead code with a drifting schema risk. This lane owned the

  **Blocking? no.**

- **R-r2-4 | server/src/Livora.Server/Platform/LivoraAuth.cs + Problems.cs (READ-ONLY platform) | `Results.Json` handler tests need `RequestServices`** |
  Not a production defect: `JsonHttpResult` resolves `IOptions<JsonOptions>` + `ILoggerFactory`

  full pipeline must supply a minimal provider (see IdentityGoogleAuthTests.TestServices). If the

  **Blocking? no.**
